# Подготовка и последовательное обновление моделей

Основной вход — `02_Обучение.ipynb`: все действия выполняются из ячеек.
Прежние ноутбуки сохранены как `*_legacy.ipynb`, выполненный исторический
`02_Обучение_результаты.ipynb` не изменяется. Старые результаты не смешиваются с новой методикой.

## Локальные данные и установка

Телеметрия и разметка остаются на компьютере, где запускается расчёт. Скрипты расчёта
не отправляют их в сетевые сервисы. Для установки библиотек нужен доступ к пакетному
репозиторию; установку можно выполнить заранее в отдельном окружении.

## Работа в ноутбуке

1. Открыть `02_Обучение.ipynb` с Python-окружением проекта.
2. В первом блоке заполнить `SETTINGS`: локальные пути, котлы, дату первого
   проверочного месяца и папку результатов. Начальные значения берутся из
   `incremental_settings.json`; редактировать JSON отдельно не требуется.
3. При необходимости задать `SENSOR_RULES`: общие имена каналов, назначения и правила
   качества. Изменения сохраняются в папке результатов, исходные правила сохраняются.
4. Выполнить **Run All**. В ноутбуке появятся аудит, режимы по нагрузке, полный реестр
   событий, обучение, таблицы сравнения и график. При проблемах источников обучение
   останавливается после показанного отчёта.
5. Для разбора другой модели/котла/периода изменить `DETAIL` и повторить ячейку графика.
   Для сохранения проверенных причин заполнить `EPISODE_LABEL_EDITS` под каталогом
   эпизодов и выполнить ячейки меток и интерпретации.
6. Для дополнительных исследований включить нужные флаги `RESEARCH` и выполнить
   последнюю ячейку. Проверке чувствительности нужны общий параметр `sensor` и дата `start`.

Отдельно запускать `.py` или редактировать CSV не нужно. Большие таблицы раскрываются
нажатием на заголовок; все строки остаются внутри ноутбука. Вывод сохраняется обычным
сохранением ноутбука, а расчётные файлы записываются автоматически в `output`.
Изменённые настройки нужно сначала применить повторным выполнением ячейки настроек.

## Необязательный запуск из терминала

Скрипты оставлены для совместимости и автоматизированных запусков. Из корня проекта:

```powershell
./.venv/Scripts/python.exe -m pip install -r training/requirements.txt
Set-Location training
../.venv/Scripts/python.exe -X utf8 run_incremental.py --audit-only
../.venv/Scripts/python.exe -X utf8 run_incremental.py
```

Пути в конфигурации задаются относительно рабочей директории. Примеры команд ниже
предполагают рабочую директорию `training`. Параметр `--config` выбирает JSON.
`incremental_settings.json` содержит пути к таблице ролей, правилам и телеметрии.
Можно задать `data_paths: {"К-5": "D:/private/К-5/hourly.parquet"}` вместо общей папки.
Первоначальное обучение и месячные обновления — один цикл, настройки fast/refit отсутствуют.
В проверенном Windows-окружении зафиксирован threadpoolctl 3.6.0: установленная ранее
версия 3.7.0 неверно перечисляла пути DLL с кириллицей и останавливала расчёт.

## Что проверить до обучения

`runs/incremental/audit/<котёл>/` содержит:

* `audit.json`: источник, дубли, ошибочные даты, нагрузка, порог и часы режимов;
* `sensor_audit.csv`: сопоставление исходных имён, общих параметров и ролей;
* `sensor_statistics.csv`: доступность, диапазон, количество различных значений;
* `load_and_modes.png`, `regimes.parquet`: нагрузка, состояния и допуск к диагностике;
* `events_to_review.csv`: события с временем отметки, предполагаемым остановом,
  неподтверждённой причиной и флагом незавершённого наблюдения;
* `quality.parquet`: пропуски и подозрительные измерения.

`source_issues.csv` перечисляет недоступные источники. Аудит возвращает ненулевой код,
если данные отсутствуют. Он не обучает модели. Нужен ручной разбор противоречий,
порогов, причин остановов и каналов с неясным назначением.

Порог определяется по прошлому до `first_test` или задаётся `run_thresholds`.
Он сохраняется; будущая история его не меняет. Короткий провал нагрузки не переписывается
задним числом в работу. Сигнал можно удерживать до `load_hold_hours`, затем состояние
становится «неизвестно». После включения действует `startup_hours`. При переносе
используется сохранённый порог донора — это требует проверки физической сопоставимости.

## Правила качества датчиков

В `SENSOR_RULES` ноутбука или `sensor_rules.json` ключами служат **общие канонические имена** из аудита, например:

```json
{
  "defaults": {"kind": "unreviewed", "mask_frozen": false, "mask_spikes": false},
  "sensors": {
    "положение механизма": {"kind": "rare", "group": "топливоподача"},
    "температура": {"kind": "continuous", "frozen_hours": 48,
      "mask_frozen": false, "mask_spikes": false, "group": "водопаровой тракт"}
  }
}
```

Это **пример структуры, а не готовые правила конкретных каналов**. Не копируйте названия
и численные ограничения без проверки. `continuous`, `discrete`, `rare`, `unreviewed`
определяют смысл канала. Длительное постоянство rare/discrete сохраняется вместе с переходом.
Для continuous подозрение на залипание записывается в признаки качества; само по себе
оно не маскирует измерение. Маскирование включается явно после проверки, допустимы
физические `min`/`max`. Проверка согласованности с соседями выполняется моделями related;
автоматически признавать датчик неисправным только по постоянству нельзя.

Пропуски цели исключаются из обучения соответствующего датчика. Необученная цель
остаётся без оценки, а прежде постоянная цель получает опорное значение и ненулевой
масштаб для обнаружения первого изменения. Эти масштабы также требуют проверки по
физическому разрешению датчика. Условия работы не входят в среднее ошибок целей.

## Месячный цикл

1. Подготовить данные общими с применением функциями.
2. На дату месяца взять подтверждённые часы работы старше `admission_delay_days`.
   Известные на эту дату аварийные окна и послеремонтные участки исключаются.
3. Отделить последние часы нормы для калибровки и предшествующий блок для проверки.
   Для временных оценок предусмотрена дополнительная предыстория калибровки.
4. При первом запуске обучить норму. При обновлении использовать только ещё не принятые
   обучающие строки; ограничение `update_rows` не запускает полный fit старой истории.
5. CatBoost продолжает ансамбль через init_model с новыми данными и ограниченным replay
   старых режимов. Память analogs/AAKR/MSET пополняется и прореживается с покрытием
   состояний/нагрузок, линейные поправки обновляются по достаточным статистикам.
   Начальные преобразования и связи ядра зафиксированы.
6. Кандидат проверяется на отложенном участке и представителях старых режимов.
   Отбраковка основана на ошибке прогноза в физических единицах, чтобы расширение
   коридора не считалось улучшением. Это проверка качества нормы, не доказательство
   улучшения обнаружения аварий. Пороги аварий не подбираются на контрольных событиях.
7. Ошибки для калибровки считаются текущей версией на не включённых в её обучение часах.
8. Предстоящий месяц рассчитывается принятой моделью. Сохраняются прогнозы до следующего
   обновления, закреплённая эталонная модель и расхождение с адаптивной.

HistGradientBoosting — явно замороженная сравнительная модель, не инкрементальная.
`cb_max_trees` ограничивает рост ансамбля. При достижении лимита новые деревья не добавляются;
нужна отдельная процедура пересмотра/сжатия модели, автоматического обучения с нуля нет.
Изменение состава признаков тоже требует отдельного согласованного перехода.

В `updates.json` записаны даты наследования, число новых строк, проверка кандидата и деревья.
`checkpoints/*.joblib` восстанавливают состояние. Изменённый код, настройки или прошлые
данные требуют **новую папку output**: продолжать несовместимую цепочку запрещено.

## Схемы тревог и качество

Максимум, top5, среднее всех, доля превышений и средние назначенных групп рассчитываются
по доступным целям. Отдельно используются текущие и усреднённые со знаком за 48 часов ошибки.
Показывается покрытие, действует `minimum_coverage`. При недостатке калибровки нет
действующего порога — это отсутствие расчёта тревоги, а не подтверждённая норма.

Тревога активируется в момент подтверждения. Первое превышение сохраняется отдельно.
`merge_hours` подавляет повторное уведомление, но не превращает промежуток ниже порога
в активную тревогу и не заполняет разрывы данных. Упреждение считается от уведомления.
Продолжающаяся старая тревога не считается новым предупреждением в окне аварии.
Её фоновая длительность учитывается независимо от пересечения с аварией.

Сравнение при бюджетах 0.5/1/2 уведомления на 720 часов и ограничении фоновой занятости:

* `comparison.csv`: исходное покрытие каждого варианта;
* `comparison_common_hours.csv`: общие рассчитанные часы одной группы/сценария/донора/получателя,
  интервалы recall с повторной выборкой целых событий и частоты уведомлений по недельным блокам;
* `*_events.csv`, `*_alarms.csv`, временные ряды parquet: события, уведомления, первое
  превышение, покрытие и месячная версия.

При малом числе аварий доверительные интервалы нестабильны. События в ремонтах ещё
требуют технологического подтверждения. Число соседних часов не заменяет число аварий.

## Варианты CatBoost

`models`: analogs, AAKR, MSET, HistGradientBoosting, CatBoost, CatBoostCorrection, CatBoostMulti.
Последние два включаются явным добавлением в список. Correction учит поправку по
ошибкам аналогов, полученным до обучения на соответствующих строках. Multi использует
общие деревья и MultiRMSEWithMissingValues с фиксированным масштабом целей.

`feature_sets`: conditions, forecast, related. Forecast использует только информацию,
известную за 1/6 часов до прогнозируемого измерения. Related требует `related_inputs`:
для каждой цели перечислить проверенные связанные датчики. Саму цель включать нельзя;
её прямые производные тоже должны быть исключены при технологическом разборе.
Без такого списка эксперимент отмечается как требующий настройки, а не подставляет
произвольных соседей. Сценарии: local, pooled, transfer. У общей схемы проверяются роли
и заявленные единицы. Transfer не обучается и не калибруется на получателе.

## Интерпретация эпизодов

`episode_labels.csv` содержит пустые поля label, label_available_at, reviewer, reason.
Suggestions — только гипотезы переключения/проблем измерения. Дата доступности метки
обязательна. Признаки берутся на момент подтверждения, без будущего максимума эпизода.
В ноутбуке каталог показан полностью; метки сохраняет ячейка `EPISODE_LABEL_EDITS`,
а следующий блок запускает интерпретацию и показывает результаты. Приведённая ниже
команда — альтернативный вход для автоматизации.

```powershell
../.venv/Scripts/python.exe -X utf8 train_interpretation.py --config incremental_settings.json --directory "runs/incremental/experiments/<эксперимент>/К-5" --unit К-5 --as-of 2026-01-01
```

Отдельные головы: характер изменения и риск за 24/168 часов. Отрицательным примерам
нужен полный горизонт наблюдения, плановый останов внутри горизонта цензурирует метку.
Есть временное разделение, разрыв между выборками, разделение групп событий и последующая
калибровка вероятностей. Малое число независимых меток даёт явный статус недостаточности.
Порог воздержания 0.7 — начальный параметр, его пригодность нужно оценить по
калибровке/ошибкам/доле неопределённых решений на реальной истории.

Флаг `--attach` присоединяет обученные головы к экспорту и обновляет манифест.
До указанной даты доступности головы историческая интерпретация остаётся неизвестной.
Самопредсказания не превращаются в подтверждённые метки. В интерфейсе выводятся
интерпретация и риски, когда соответствующие головы доступны; иначе смысл не определён.

## Дополнительные исследования

В ноутбуке эти действия доступны через `RESEARCH`, таблицы выводятся в последнем блоке.
Команды ниже нужны только при отдельном запуске из терминала.

```powershell
../.venv/Scripts/python.exe -X utf8 run_experiments.py ensemble --config incremental_settings.json --unit К-5
../.venv/Scripts/python.exe -X utf8 run_experiments.py survival --config incremental_settings.json --unit К-5 --as-of 2026-01-01
../.venv/Scripts/python.exe -X utf8 run_experiments.py sensitivity --config incremental_settings.json --unit К-5 --model "<экспорт>" --sensor "<общий параметр>" --start 2026-01-01
```

Ensemble сохраняет совместные признаки нескольких детекторов. Survival — исследование
Cox с недельными наблюдениями, разделением жизненных циклов и правым цензурированием.
Информативность плановых вмешательств ограничивает трактовку результата. Sensitivity —
искусственные скачки, дрейф, залипание, задержка и сдвиг канала баланса. Последний не
является полной физической симуляцией. Синтетические результаты не подтверждают
качество на реальных авариях и не используются автоматически для промышленной разметки.

## Проверка экспорта и дашборд

Экспорт содержит state.joblib, model.py, собственный runtime, kernel_models.py, config.json,
sensors.csv и SHA-256 manifest.json. Проверка сохранённой модели — в ноутбуке 03.
Пакет требует установленных зависимостей, но не исходной папки проекта. Код проверяет
целостность и отказывается молча использовать отличающийся закэшированный runtime.
Загружайте только собственные доверенные joblib-артефакты.

В дашборде MODEL_DIR указывает на этот экспорт, MODEL_VIEW — например `mean::instant`.
Подготовка выполняется самим пакетом. Для исторического просмотра нужна соответствующая
месячная версия; текущий итоговый экспорт нельзя выдавать за исторически доступную модель.

## Что подтверждено без конфиденциальной телеметрии

Автотесты проверяют каузальность, сохранение редких переходов, наследование деревьев,
обновление статистик и памяти без полного fit, корректное время уведомления, пропуски,
перенос, восстановление цепочки и переносимость экспорта. Они не определяют технологически
верные пороги, причины аварий, физические группы каналов или лучшую модель для реального котла.
Эти проверки выполняются локально владельцем данных по сохранённым отчётам.

Полный демонстрационный прогон с генерируемыми данными:

```powershell
../.venv/Scripts/python.exe -X utf8 run_validation.py --output runs/my_synthetic_validation
```

Папка должна быть новой. Скрипт проверяет семь моделей, прогноз на час вперёд,
месячные обновления, объединённые признаки, чувствительность и корректный отказ
обучать интерпретацию/время до отказа при недостатке событий. Все результаты
помечены SYNTHETIC_ONLY. Для проверок реализации из корня проекта:

```powershell
./.venv/Scripts/python.exe -X utf8 -m unittest discover -s training/tests -v
```
